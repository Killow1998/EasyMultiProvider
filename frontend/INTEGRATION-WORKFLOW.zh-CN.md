# EMP v0.12.11 集成构建与验收流程

编写时间：2026-10-05 11:08 Asia/Shanghai。

本文是准备与交付方案，尚未安装工具链、注册 CI Runner、建立远程仓库、
执行 Rust 测试或发布程序。当前前端修改仍在本地，未暂存、未提交。

## 1. 一台电脑的职责

先以一台 macOS 电脑建立集成构建环境。它接收确定的源码输入，运行测试，
产出当前平台的测试程序、校验值和报告。其他开发者不需要安装 Rust，
测试者不需要获取全部源码。

EMP 管理服务仍绑定测试者本机的 loopback。构建机向团队交付程序和报告，
不把 EMP 管理端口开放成团队共享服务。单台 macOS 的结果只覆盖实际测试的
系统和架构；Windows、Linux 和另一种 macOS 架构分别增加构建/验收环境。

| 职责 | 输入 | 输出 |
| --- | --- | --- |
| 前端开发 | Web 源码、接口约定、模拟场景 | 页面资产、前端测试、版本说明 |
| 后端开发 | 后端源码、依赖和行为约定 | 指定后端版本、接口测试、变更说明 |
| 集成构建 | 确定的前后端输入 | 可运行程序、SHA-256、构建记录、自动测试报告 |
| 验收 | 同一个测试程序、隔离配置、验收用例 | 请求/恢复证据、通过或失败结论 |
| 发布 | 已通过验收的同一个产物 | 经授权的分发；独立于内测构建 |

## 2. 一次性准备

1. 确认电脑的 OS、CPU 架构和本轮目标。首次只承诺这一平台。
2. 建立专用构建系统账号，不在该账号登录日常模型账户。另设桌面验收账号，
   用于需要 GUI、托盘、系统钥匙串和真实 Codex 的测试。
3. 安装 Git、官方 rustup、Rust 1.93.1 和该平台的编译工具。macOS 要有命令行
   编译工具。前端 Node/npm 固定到经过验证的版本；本轮已测试的是 Node
   26.0.0 / npm 11.12.1。使用 Cargo.lock 和 package-lock.json，构建时不更新依赖。
4. 设置专用工作目录，分开输入、任务、产物和报告。每次任务使用新的 source
   目录，避免覆盖仍在编辑的开发 checkout。下载依赖需要的网络/代理在构建
   环境配置一次；不要把包含凭据的代理配置写进源码或报告。
5. 用受限内部目录交付测试包。先手动运行同一套命令，成功后再接 CI。
6. 后续选择团队私有 Git 仓库作为唯一源码入口。当前不提交阶段使用受控的
   源码输入包和 SHA-256，不能把有未记录修改的目录称为某个 Git commit。

建议目录结构（均为示意目录，尚未创建）：

```text
emp-integration/
  inputs/<input-id>/              # 冻结的源码输入
  jobs/<build-id>/source/         # 本次独立构建目录
  artifacts/<build-id>/           # 不可覆盖的程序与校验值
  reports/<build-id>/             # 清理敏感信息后的报告
```

工具链安装来源：<https://rust-lang.org/tools/install/>。

## 3. 本次前端如何交给构建机

后端基线固定为：

```text
v0.12.11
a568d005b4fc32793ec8e06db7d5891324a1c142
```

前端输入包括两处修改的原有文件和新建的 frontend/ 文件：

- crates/emp-app/web/index.html
- crates/emp-app/web/style.css
- frontend/ 下的构建、预览、测试和产品页源码，以及必要文档

当前已提交文件的修改可用 patch 交付；未提交的新文件也必须纳入输入包。
排除 node_modules、dist、凭据、真实配置、会话文件、真实日志和临时文件。
用明确文件清单组包，并记录输入包校验值。保留原始前端 checkout。

构建机从基线建立本次 source 目录，应用前端输入，然后运行
`verify:baseline`。它应确认除两处 Web 文件外的 505 个原有文件仍完全一致。
该检查只适用于本次“前端改变、后端冻结”的交付；后端改变时需要明确新的
基线和变更范围，不能简单沿用这项结论。

完整项目首次只需要准备在构建环境中。前端日常继续以页面资产、接口约定和
模拟服务工作。由于本版 Rust 使用 include_bytes! 嵌入 Web 文件，最终程序
由集成构建环节重新打包。现有模拟预览不直接视为真实后端联调入口。

## 4. 每次内测候选执行的流水线

以下命令在本次 source 根目录执行。任一步失败都停止交付“通过”的产物，
保留失败报告。本次前端的 18 项 Node 测试已经在开发机通过，但以下 Rust
阶段和原生打包仍待在构建环境实际执行。

```sh
npm --prefix frontend ci --ignore-scripts
node --test crates/emp-app/tests/web_features_contract.cjs
npm --prefix frontend test
npm --prefix frontend run build
npm --prefix frontend run verify:baseline
git diff --check

cargo +1.93.1 fmt --all -- --check
cargo +1.93.1 clippy --locked --workspace --all-targets -- -D warnings
cargo +1.93.1 test --locked --workspace --all-targets
cargo +1.93.1 xtask package
cargo +1.93.1 xtask package-smoke
```

首次诊断真实进程测试入口，可以先单独运行：

```sh
cargo +1.93.1 test --locked -p emp-app --test user_journeys
```

正式候选的 workspace 测试已包含此测试，不需要重复执行它。
`xtask package` 产出当前平台的 artifacts/ 程序、安装包和 SHA-256 文件。
`package-smoke` 检查隔离的更新/安装路径，不等于真实用户桌面行为验收。
原生 GUI 验收还需登录的测试桌面会话。

每次将 artifacts/ 的结果复制到独立 build-id 目录，禁止后一轮覆盖上一轮。
后台源码没有变化时，也要确认最终程序确实包含本轮前端资产。

## 5. 每个包附带的交付记录

程序继续报告原版 0.12.11 时，用外部 build-id 区分不同前端候选，不把它们
混称为上游 v0.12.11。每个 build-id 至少记录：

- 后端 commit、前端 commit；未提交输入则记录输入包 SHA-256 和文件清单。
- OS/架构、Rust/Node/npm 版本、Cargo.lock/package-lock.json 校验值。
- 构建命令、程序/安装包 SHA-256、构建时间（Asia/Shanghai）。
- 各项自动测试的实际退出状态与报告链接。
- 原生验收所用 Codex 版本、验收结论、失败项和验证范围。
- 请求恢复、模型路由、工具调用、对话连续性等分别记录，未测写“未验证”。

建议交付状态：构建失败、自动检查通过待验收、验收失败、验收通过。
仅“验收通过”的同一个程序进入后续发布步骤，不重编译一个未知输入的新包。
交付记录和公开报告不包含账户身份、密钥、登录链接或私人对话内容。

## 6. 验收环境

先使用模拟凭据、本地模拟上游和专用测试目录；真实请求阶段再使用指定测试
账号及预算。构建账号不保存真实模型凭据，真实验收不由普通源码任务自动触发。

EMP 配置、CODEX_HOME、native_catalog_path、账户/密钥存储、日志和测试工作区
均指向专用测试位置。显式关闭 auto_enable_on_start，初始不开启额外模型/搜索
探测。使用独立端口。不要复制整个日常 .codex 或私人历史作为测试输入。

CODEX_HOME 不会自动隔离系统钥匙串与所有系统集成。测试桌面 App 和托盘时，
使用专用 OS 测试用户；不能把当前正在运行的日常 Codex 当作隔离客户端。
每次任务只清理自己持有的目录/进程，不能全局终止 EMP/Codex 进程。

| 场景 | 必须留下的证据 |
| --- | --- |
| 页面读取、编辑、导入 | 真实 API 返回、持久化结果、刷新/重启后结果、界面截图 |
| 失败和重试 | 未覆盖已有数据、失败阶段准确、重试未重复导入/应用 |
| 真实请求 | Codex 输出、完整终止事件、所选路由的日志证据 |
| 工具与切换 | 只读工具执行/回传；切换路由和历史继续的独立证据 |
| 正常退出/恢复 | 进程退出、端口释放、拥有字段恢复、其他用户字段保留 |
| 恢复后的可用性 | 新启动测试 Codex 绕过 EMP 成功请求；需要时测试恢复原对话 |
| 活动请求/恢复冲突 | 明确拒绝或失败状态，服务/数据仍符合预期 |
| 异常终止 | 仅在可丢弃测试环境操作；后续恢复路径和数据结果 |
| 桌面/托盘 | 测试用户实际启动、打开管理页、退出及恢复 |

页面断连和 `status: stopping` 不是完整验收证据。当前前端没有修复原版后端
的退出/恢复问题，联调发现后端失败时仍应据实阻止通过。
保留原版更新功能，但独立前端内测不要通过上游更新覆盖待验收程序。

## 7. 从手动流程接入 CI

手动首轮成功后，将上述命令与交付记录固化成脚本，再让 CI 调用同一脚本。
先每台机器串行一个任务，特别是 GUI 和生命周期验收。

可以将专用机器接为私有仓库的 self-hosted runner。构建账号只拿必要源码读取
和内部产物写入权限；发布凭据与真实模型凭据放在独立受控阶段。该 Runner
只执行授权的可信来源代码，不开放给任意外部 PR。更严格隔离时，每任务使用
可重建环境。需要的 CI 能力是构建、测试、保存报告和产物，不必先搭建庞大平台。

原仓库已有 runtime-compatibility.yml 和 package.yml，可复用其中命令。
package.yml 包含由 tag 或发布输入触发的 Release 步骤，因此内测要设置独立的
仅构建工作流，不通过发 tag 来申请测试包。当前未修改或启用任何远程工作流。

参考：

- <https://docs.github.com/en/actions/concepts/runners/self-hosted-runners>
- <https://docs.github.com/en/actions/reference/security/secure-use>

## 8. 第一轮完成标准

前端开发者在自己的电脑完成修改和模拟测试；构建机用可识别的同一份输入
产出程序；验收者不装开发工具、不拉全套源码即可运行这个包；报告能说明
哪些行为实际通过；失败能回到对应前端或后端版本；全过程未影响日常配置。

此时才形成了可重复的团队交付流程。后续增加私有 Git/PR 审查、CI 调度和
多平台任务是在同一流程上扩展，不改变已验证的交付边界。
