# EasyMultiProvider v0.6 Specification

Status: implemented; offline release gate passed and core user acceptance recorded

Gemini live acceptance is deferred because the configured AI Studio quota is
currently exhausted. This does not block v0.6: Gemini compatibility remains
covered by offline protocol and catalog regressions, while current-login,
imported-subscription, GLM, and ox-alpha routes have supplied the live product
evidence used for this release.

## 1. Release objective

v0.6 makes model identity, model capabilities, and cross-provider task
continuity reliable across the Codex CLI, TUI, and ChatGPT desktop app.

The release theme is **portable model switching and capability truth**.

Codex remains the only owner of threads, history, resume, compaction, agents,
permissions, and tools. EMP owns destination-aware request projection, routing,
catalog generation, capability metadata, transport diagnostics, and encrypted
credentials. EMP must not introduce a second history database.

## 2. Non-negotiable constraints

- Preserve native Codex sessions and `resume` behavior.
- Preserve native subscription models and imported subscription routes.
- Do not disable WebSocket, native HTTP fallback, remote compaction, MCP,
  authentication, or other native Codex features.
- Do not store prompts, assistant content, reasoning text, tool arguments, tool
  output, or complete request/response bodies in diagnostics or accounting.
- Do not silently discard user messages, images, or paired tool calls.
- Do not replay model generation after visible output or a tool call has been
  emitted.
- Do not modify Codex's state database or rollout JSONL files.
- Do not stop or reconfigure the EMP instance carrying the implementation or
  verification task. Runtime tests use an isolated temporary state and port.
- Do not commit API keys, auth files, local provider names, local endpoints,
  personal paths, session identifiers, or private test data.
- Do not run Codex Security as an implementation or release gate.
- Do not create a Git tag unless the user explicitly requests it.

## 3. Canonical model identity

Every routed model has one canonical slug. The slug is the stable route key and
must be unambiguous across providers.

Catalog display rules use a right-aligned five-character context field followed
by two spaces and the model label:

- current native login: `[ 258K]  GPT-5.6-Sol`;
- imported subscription: `[ 258K]  team · GPT-5.6-Sol`;
- every external provider, without vendor-specific branches: exact canonical
  slug after the context field, for example `[ 250K]  provider/glm` or
  `[1.05M]  provider/stealth/ox-alpha`.

All external providers use the same formatter. OpenRouter, Gemini, LiteLLM,
self-hosted gateways, and custom providers do not receive separate label logic.
The upstream friendly name may appear in the description but must not replace
the canonical route in `display_name`.

The context field uses compact uppercase `K`/`M` units and an interior width of
five characters (` 258K`, `1.05M`). Unknown context uses a fixed unknown marker
so following model names keep the same start column. The generated `slug`
remains the exact value accepted by `/model`.

Catalog order is also the grouping mechanism because Codex exposes no safe
non-selectable group-heading entry:

1. current-login native subscription models;
2. imported subscriptions in account configuration order;
3. external providers in provider configuration order;
4. within each group, newest known release first, then older and undated models.

Hidden models remain absent from the exported list. EMP must never insert a
selectable fake model as a visual group separator.

## 4. Responses dialect model

`responses` is a protocol family, not a promise that every endpoint accepts the
full Codex-native item dialect. EMP separates transport protocol from request
dialect.

Initial dialects:

- `codex_native`: full native Codex/OpenAI subscription exchange;
- `portable_responses`: allowlisted Responses subset for external compatible
  APIs, gateways, and LiteLLM-style deployments;
- `chat_completions`: existing Responses-to-Chat translation;
- `anthropic_messages`: existing Responses-to-Anthropic translation.

Provider protocol selection remains `auto`, `responses`, `chat_completions`, or
`anthropic`. Dialect selection is internal evidence used after route resolution.
Manual protocol selection remains authoritative; EMP must not reinterpret an
authentication, WAF, rate-limit, timeout, or generic server failure as a
protocol rejection.

### 4.1 Native destination

Imported subscription routes use native passthrough semantics for metadata and
native state that originated from a compatible native route.

When history contains state produced by an external provider, EMP creates an
ephemeral destination view:

- preserve visible user and assistant messages;
- preserve text and image content in order;
- preserve valid function-call and function-call-output pairing;
- omit external plaintext reasoning items that cannot be represented as native
  opaque reasoning state;
- never convert raw chain-of-thought into a user-visible message;
- preserve final assistant output independently from discarded reasoning state.

### 4.2 Portable Responses destination

External API-key Responses routes receive an allowlisted payload:

- supported top-level generation controls;
- user/assistant messages with supported text and image parts;
- standard function calls and paired outputs;
- normalized compaction summary messages when EMP can safely decode them;
- no Codex client telemetry, private thread metadata, native-only opaque state,
  or unsupported item fields.

An unsupported item that affects visible content or tool integrity causes a
clear bounded error. The error identifies only item index, item type, content
part types, and normalized failure class. It does not include content.

Portable tool projection must cover the Codex runtime tool surface, not only a
hand-written function fixture:

- preserve standard function definitions and function call/output pairing;
- translate a Codex custom tool to a portable function only when its input and
  output contract can be represented without semantic loss;
- map the upstream call back to the Responses item type and identifier expected
  by Codex before Codex executes the tool;
- keep Codex-owned tools, including web/search tools, under Codex permission and
  execution control; EMP routes their schemas and calls but never performs a
  hidden search on the model's behalf;
- reject a non-representable tool type explicitly using only its safe type, not
  its name, arguments, output, or schema content;
- preserve tool-call identifiers across the complete call/output round trip so
  the next model turn can consume the result.

When EMP owns Codex's configured `openai_base_url`, Codex-owned auxiliary
requests such as `POST /v1/alpha/search` also arrive at EMP. EMP forwards that
endpoint to the native Codex service with the caller's existing session
authentication. It does not implement its own web-search tool, retain search
queries, or give external models direct network credentials.

### 4.3 Response projection

External plaintext reasoning output must not be returned to Codex as native
reasoning state. EMP preserves the final assistant output and valid structured
tool calls. Reasoning summaries are passed only when the target contract
explicitly supports them; raw reasoning text is never retained as an opaque
native state substitute.

The projection is per request and ephemeral. EMP may keep bounded numeric
accounting metadata and provider/model fingerprints, but never conversation
content.

### 4.4 Safe fallback

Protocol fallback is allowed only when all conditions hold:

1. the provider protocol is `auto`;
2. the first candidate fails with a definitive protocol/schema rejection;
3. no text, reasoning summary, image output, or tool call has been emitted;
4. the alternate candidate is a concrete protocol adapter supported by EMP for
   that authentication mode;
5. only one fallback attempt is made, and a successful result is recorded for
   that endpoint, deployment, and model identity.

There is no fallback for authentication, permission, WAF, rate-limit, context
length, network, timeout, or generic 5xx failures.

## 5. Capability truth

Capabilities have a value, source, and confidence. Sources include official,
advertised, observed, manual, inherited, inferred, and unknown. Manual
overrides survive refresh.

### 5.1 Modalities

- Read OpenRouter-style `architecture.input_modalities` when present.
- Unknown input modalities default conservatively to `text`.
- Preserve internally known modalities even when Codex cannot expose them.
- Export only modalities supported by the Codex catalog contract.
- Image input support is independent from
  `supports_image_detail_original`.

### 5.2 Reasoning

Reasoning support and reasoning effort levels are separate capabilities.

- Parse advertised reasoning support, including OpenRouter-style supported
  parameter metadata.
- Use exact effort levels only when advertised, observed by a bounded explicit
  probe, or manually configured.
- A generic indication that `reasoning` is supported must not fabricate
  `low`, `medium`, `high`, or another level set.
- If reasoning is supported but levels are unknown, record that state and omit
  an effort value unless the user supplies a manual override.
- A model with no reasoning control remains usable; requests omit effort.
- Existing context, visibility, and capability overrides survive discovery.

### 5.3 Context

Continue exporting the known usable context window in the model display name
and catalog fields. Unknown limits remain unknown. Context Guard behavior from
v0.5 remains intact and is not replaced by a history store.

## 6. Model discovery and visibility

The existing discovery UX is a required v0.6 regression boundary:

- already imported models are selected;
- newly discovered models are not selected;
- search matches model ID and display name;
- `全选` and `全不选` apply to the currently visible filtered result;
- the selection count is visible;
- only selected models are imported;
- refresh preserves hidden state and manual capability overrides.

Per-account model visibility, duplicate-current-login filtering, internal model
filtering, and provider-wide show/hide remain supported. v0.6 must not regress
them while changing catalog labels.

## 7. WebSocket reliability

EMP must distinguish:

- client disconnect or cancellation;
- EMP client-facing WebSocket close;
- upstream close before first output;
- upstream close after partial text;
- upstream close after a tool call;
- malformed or missing terminal event;
- proxy/network reset;
- successful reattachment to the same running task;
- native WebSocket-to-HTTP fallback.

Diagnostics contain only transport, close code, normalized failure class,
whether output/tool activity occurred, whether a terminal event was observed,
and whether recovery succeeded.

Recovery requirements:

- a reconnect that completes the same task is recorded as recovery, not task
  failure;
- visible output and tool calls are delivered exactly once;
- generation is never replayed after output or a tool call;
- a pre-output generation retry is permitted at most once and only when safe;
- after partial output, use protocol-defined reattachment when available;
  otherwise fail explicitly;
- each request emits exactly one terminal success or failure;
- native WebSocket and HTTP fallback remain enabled.

## 7.1 Incomplete and truncated output

EMP must not turn an upstream incomplete response into a normal successful
completion. For every supported upstream protocol it records and translates:

- Chat Completions `finish_reason`, including `length`, content filtering, tool
  calls, and normal stop;
- Responses `status=incomplete` and its bounded incomplete reason;
- a stream ending without a terminal event;
- an explicit upstream output-token limit.

`finish_reason=length` or the corresponding Responses incomplete status is
reported to Codex as an incomplete/failed terminal that explains the normalized
reason without including response content. It is not emitted as
`response.completed`. A normal `stop` remains successful; `tool_calls` remains
an in-progress tool boundary rather than truncation. Diagnostics distinguish
`output_limit`, `content_filter`, and `stream_incomplete` without storing text.

## 8. External models as native Codex workers

Codex CLI `0.149.0` exposes a native `spawn_agent` model override and resolves
that override through the same model catalog used by `/model`. EMP therefore
supports external child models through that native path. It does not emulate
subagents with a hidden `codex exec`, a second session store, or an EMP-owned
supervisor.

The runtime contract is:

- use the same catalog slug as interactive `/model` selection;
- Codex owns the child task, permissions, sandbox, workspace, tools, and result;
- EMP supplies routing and honest model capability metadata;
- reasoning effort is optional and omitted for models without that control;
- image capability is required only for a worker input containing images;
- EMP does not copy the native template's `multi_agent_version` onto external
  entries because that field describes the model's own collaboration backend,
  not whether Codex may delegate a task to it;
- visibility in the catalog means the route can be requested, not that every
  external model is guaranteed to be a reliable coding worker.

Provider quality and structured tool-call behavior remain model-specific.
GLM and ox-alpha have completed the v0.6 child-model acceptance path; visibility
in the catalog is still not a guarantee that every future Provider model is a
reliable coding worker. Failure of one Provider route does not cause EMP to
replace Codex's delegation semantics.

## 9. Privacy-safe observability

Required diagnostics may include:

- route and provider fingerprints derived from non-secret stable identifiers;
- request item count and item type sequence;
- content part type sequence without content;
- tool-call/output pairing status without names or arguments;
- selected protocol and dialect;
- response status and normalized error class;
- stream lifecycle flags and timings.

Diagnostics must not include raw prompts, assistant text, reasoning text, tool
arguments, tool output, authorization headers, API keys, auth tokens, private
URLs, local filesystem paths, or response bodies.

## 10. Delivery slices

### Slice 1: P0 dialect bridge and cross-provider history

- add dialect classification;
- add privacy-safe shape diagnostics;
- implement native and portable request projections;
- prevent external plaintext reasoning from becoming native reasoning state;
- preserve visible output, images, and tool pairing;
- implement strictly bounded safe fallback;
- cover both fresh external requests and already contaminated task history.

### Slice 2: P0 canonical labels

- apply one external-provider display formatter;
- retain imported subscription formatting;
- prevent duplicate context suffixes;
- verify App/TUI route identity remains unambiguous.

### Slice 3: P1 capability truth and discovery regression

- discover reasoning support separately from exact effort levels;
- persist capability source/confidence and manual overrides;
- omit unsupported or unknown effort parameters;
- retain existing search, selection, visibility, modality, and context behavior.

### Slice 4: P1 WebSocket reliability

- add boundary diagnostics;
- add terminal-event and exactly-once invariants;
- add safe recovery behavior without generation replay;
- preserve native fallback.

### Slice 5: P2 native external worker integration

- verify the native `spawn_agent` model override in Codex `0.149.0`;
- keep one catalog slug for interactive and delegated use;
- prevent external entries from inheriting false agent-backend metadata;
- preserve Codex ownership of task lifecycle, permissions, tools, and history.

## 11. Verification

Implementation and verification run in the current checkout without modifying
the active EMP instance. Runtime acceptance uses isolated temporary state and
ports.

Required automated regressions:

1. portable Responses removes unsupported native-only state while preserving
   text, URL/base64 images, and paired function calls;
2. native destination removes external plaintext reasoning and preserves final
   assistant output;
3. fresh portable GLM-style request no longer contains unsupported item shapes;
4. external-to-native and native-to-external fixture histories remain usable;
5. all external catalog entries use `[context] provider/model` with one shared
   formatter;
6. two providers exposing the same upstream model remain unambiguous;
7. reasoning support without exact levels does not invent effort options;
8. manual context, reasoning, and visibility overrides survive refresh;
9. discovery search, `全选`, `全不选`, and selection defaults remain correct;
10. reconnect recovery delivers one terminal result without duplicate text or
    tool calls;
11. protocol fallback occurs only for a safe pre-output schema rejection;
12. diagnostics contain shapes and states but no content or credentials.
13. an external catalog entry keeps its exact slug, remains API-addressable,
    and does not inherit the native template's collaboration backend.

Required real acceptance after automated verification:

- CLI/TUI: native login, imported subscription, and external model are visible;
- ChatGPT desktop on macOS: external labels include the provider prefix;
- a fresh external GLM-style route answers normally;
- external reasoning model to two imported native subscription routes works in
  the same task;
- native to external to native switching works in the same task;
- one image request and one structured tool-call round trip succeed;
- the routed external reasoning model completes one bounded read-only Codex
  tool call and one Codex-controlled web/search tool round trip without saying
  that tool invocation failed;
- a recovered reconnect completes once without duplicated output;
- native `resume` continues to show the same tasks.

Live credentials and Provider endpoints remain user-local. Automated tests use
generic fixtures. A live-provider limitation is reported as unverified rather
than replaced by a credential-bearing test.

## 12. Completion boundary

v0.6 is complete when Slices 1 through 5 pass their focused regressions and the
release gate confirms that no local configuration, credential, generated
catalog, or planning artifact enters the commit. Live Provider quality remains
an acceptance result rather than a catalog promise. The user authorized the
v0.6 commit and `main` push; no Git tag is created.
